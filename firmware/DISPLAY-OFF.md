# Отключение внешнего видеосигнала на XREAL One Pro

Задача: оставить на очках только их собственный вывод (плеер, интерфейс пилота),
а картинку с хоста (Mac/ПК по USB-C DP alt-mode) убрать. Питание и USB-данные при
этом должны остаться — по SSH очки должны быть доступны.

## Что в итоге даёт нужное состояние

Панель без кадров от хоста живёт нормально и продолжает показывать наш OSD-слой.
Проверено на устройстве:

```
OLED overlay ready: 1280x720 -> 1920x1080 on both eyes (buffers=3, cached_mmz=3/3)
Playing ./videosample.mp4
DisplayClient I: DP get 0, 0 failed, dp vsync 0
Shown 1799 frames, dropped 0 late frames.
```

То есть при `DP get failed` (нет синхронизации с DP) плеер всё равно выводит картинку,
`pilot` отвечает на кнопку на дужке, а затемнение линз (электрохромный слой) держится.

Внешне это выглядит как штатное «No video signal» / «видеосигнал не обнаружен» —
то же состояние, что при подключении к пауэрбанку.

## Что НЕ отключает видеосигнал (проверено)

| Способ | Результат |
| --- | --- |
| `set_hpd_status(0)` через `/dev/ar_dprx` (ioctl `'d',2`) | связь моргает и восстанавливается; кадры продолжают идти |
| `disable`/`clear` VO-слоёв 0 и 0x1000 | на DP-видео не влияет вообще: картинка остаётся живой и интерактивной |
| `kill -9 media_service` | картинка **замерзает** последним кадром, но не исчезает; процесс остаётся в состоянии `D` и требует перезагрузки |
| выключение слоя 1 (`0x100`) | недоступно (`-1`): это слой пилота |

DP-поток идёт мимо VO-слоёв, внутри `coconut_dprx` (`dprx-coconut a0a0000.dp`),
поэтому управлять им через VO-таблицу нельзя.

## Как получить чёрный дисплей — рабочая процедура

Отключать надо **со стороны хоста (Mac)**. Очки сами кадры не гасят, но если хост
перестаёт их выдавать, панель уходит в «нет видеосигнала»: чёрный экран, питание и USB
живы, `pilot` отвечает на кнопку, SSH работает.

### 1. Посмотреть, как система видит очки

```
export PATH=/opt/homebrew/bin:$PATH        # displayplacer из brew
displayplacer list
```

В выводе будет отдельный экран — у нас это выглядело так:

```
Persistent screen id: 5B3B753B-D2F4-4E58-8853-ED2ED5DDD783
Contextual screen id: 2
Serial screen id: s0
Type: 105 inch external screen
Resolution: 1920x1080
Hertz: 60
```

Три равнозначных способа адресовать этот экран: `id:5B3B753B-…`, `id:2`, `serial:s0`.
Если persistent id не находится (macOS пересоздаёт запись), работают `id:2` и `serial:s0`.

### 2. Выключить выход на очки

```
displayplacer "serial:s0 enabled:false"
```

Эквиваленты: `displayplacer "id:5B3B753B-D2F4-4E58-8853-ED2ED5DDD783 enabled:false"`
или `displayplacer "id:2 enabled:false"`.

Признак успеха — панель очков чёрная, а `displayplacer list` больше не показывает
XREAL. Строки вида

```
Unable to find screen 5B3B753B-… - skipping changes for that screen
```

это **не ошибка**: экран уже отключён, поэтому его и не находят. Повторный вызов
команды на уже выключенном выходе даёт именно это сообщение.

### 3. Проверить, что состояние нужное

На Mac:

```
displayplacer list | grep -c "1920x1080"      # 0 — очков в списке нет
system_profiler SPDisplaysDataType | grep -c Resolution   # только встроенный экран
```

На очках (SSH продолжает работать):

```
dmesg | tail -20        # ожидаемо: coconut_typec_reset_assert / dprx_init_phy / deassert
cat /sys/class/extcon/*/state   # DP=1 — линк держится
```

Глазами: панель чёрная, интерфейс пилота (кнопка на дужке) отвечает.

### 4. Вернуть картинку

```
displayplacer "serial:s0 enabled:true"
```

Если экран не находится и после этого — переподключить кабель: macOS пересоздаёт
запись дисплея только при переинициализации Type-C/DP-PHY.

### Почему у другой модели не получается

Скорее всего пробуют гасить картинку **на самих очках** — через HPD, VO-слои или
убивая `media_service`. Это не работает (таблица выше): DP-поток идёт мимо VO-слоёв,
HPD только моргает линком, а `media_service` оставляет последний кадр замороженным.
Гасить нужно выход на хосте.

Резервный путь, если хост недоступен: подключить очки кабелем/адаптером **без
DisplayPort alt-mode** (только питание и USB-данные) — получится тот же чёрный экран
с живым SSH.

## Что видно в dmesg при отключении

```
coconut_typec_reset_assert 1517 5
coconut_typec_comphy_configure 898 conf 4 2700
coconut_dprx_init_phy 905 get lane info 4 4 1!
coconut_typec_reset_deassert 1546 5
```

Это сброс Type-C/DP-PHY, который происходит, когда хост снимает дисплей. После него
линк и VBUS остаются, очки показывают «нет видеосигнала», SSH продолжает работать.

## Важные ограничения, обнаруженные по пути

- После `kill -9` плеера `pilot` остаётся остановленным (`SIGSTOP`) — он мигает и не
  реагирует. Лечится `kill -CONT <pid>`. Плееру нужен сторож, который возобновляет
  пилота при аварийном завершении.
- Отключение слоёв 0/0x1000 и последующая попытка их включить обратно приводят к
  `enable_osd_vo_layer: enable vo0 channel failed` — канал поднимается только после
  перезагрузки.
- Частота развёртки панели, измеренная через `NRVsyncSetCallback`/`NRVsyncStart`
  (`vsprobe`), — около 121.9 Гц, но тики перестают приходить, когда `pilot`
  остановлен, поэтому как источник синхронизации для плеера он не годится.

Сборка, запуск и все флаги плеера — в [PLAYER-RUNBOOK.md](PLAYER-RUNBOOK.md).

## Воспроизведение в этом режиме (что выяснено на устройстве)

Всё ниже проверено при выключенном внешнем сигнале — то есть в том состоянии, ради
которого всё делалось.

**Аппаратный декод.** Флаг `--hwdecode` в плеере работает и даёт идеальные метрики:
900 кадров за 15 с, 0 опоздавших, интервал показа 16.7 мс. Внутри обёртка
`libxrlinux_codec.so` сама грузит `libmpi_vdec.so`/`libhal_vdec.so` и вызывает
`AR_MPI_VDEC_*` — то есть MPI рабочий, проваливалась наша ручная инициализация,
которая попадала в залипание CUSE `/dev/vctrl`. Софт-декод (4 потока ffmpeg) на
4×Cortex-A 1.272 ГГц не тянет 720p60: 254 % CPU и половина кадров мимо.

**Звук.** Сервис `NRAudioPlayWavFile` принимает только:
- канонический PCM WAV (тег `01 00`, fmt-чанк 16 байт) — файл `WAVE_FORMAT_EXTENSIBLE`
  от ffmpeg проглатывается молча (`return[0]`) и не звучит;
- файл, лежащий **в `/tmp`** (путь в `/usrdata/...` тоже принимается без ошибки, но
  тишина);
- при остановленном на время воспроизведения `pilot` — аудио-маршрут держит он.

Сервис **не склеивает клипы**: он перезапускает воспроизведение на каждый файл, и на
каждом стыке теряются десятки миллисекунд. Проверено непрерывным тоном, нарезанным
на секундные куски (подача и за 960 мс, и ровно в длину файла) — слышны провалы на
каждом стыке; один цельный 10-секундный клип идёт идеально. Поэтому клип в плеере
увеличен с 960 мс до 20 с: провалы раз в 20 секунд вместо раза в секунду.

**Дрожание картинки.** Панель тактуется примерно на 121.9 Гц (измерено `NRVsyncSetCallback`,
интервал 8.21 мс, разброс 5.48–8.62), контент 60 к/с. Плеер отдавал кадр «когда готов»,
поэтому интервал показа гулял 8.5 / 16.7 / 24.8 мс — кадр попадал то на один тик
развёртки, то на три. Это и видно на вертикальных панорамах. Тики дисплей-сервиса как
источник синхронизации не годятся: они перестают приходить при остановленном пилоте,
а измеренная частота плавает (121.9 → 123.3 Гц). Текущая правка: кадр готовится
(масштаб и композиция) **до** своего дедлайна, к моменту показа остаётся только
отправка — это убирает из критического пути подготовку и отправку и сжимает разброс
интервала с 24.8–32.9 мс до 18.0 мс.

**Ограничение по разрешению.** OSD-слой в родных 1920×1080 выделяется
(`OLED overlay ready: 1920x1080 -> 1920x1080 ... buffers=2`), но на панель ничего не
выводит — картинки нет. Рабочий путь: кадр 1280×720 в OSD-слой, масштабирование в
аппаратном скейлере VO до 1920×1080, три буфера.
